# Consolidated Phase 8C engineering pilot (8C.final.1)

## Status and threat model

This release consolidates the runnable local implementation of 8C.2B–8C.3. It **does not complete untrusted-student execution qualification**. Do not use it to automatically run arbitrary student source on a personal Windows host. It does not change `approved_snapshots`, declare a new worker attested, accept a caller's claim of qualification, or bypass the existing exact-SHA VM gate. The legacy reviewed runtime remains the authority for actual execution. Existing 8C.1 assessment remains conservative and unchanged.

The operator controls config, trusted runtime hashes, the controller code and the fresh output directory. Same-operator compromise, QEMU/hypervisor escape, hostile guest attacks on the host's services, unbounded host process writes outside the managed volume, and independently verified worker provenance are not addressed by a report checksum. No synthetic test or successful reviewed run promotes these limitations to PASS.

## What is implemented

* **8C.2B**: deterministic, bounded, stable-wheel PyPI resolver for exact direct pins (no extras/direct URLs/source builds), Linux x86_64 CPython 3.12.x, portable manylinux <= glibc 2.17 or pure Python wheels. Up to 25 direct pins, 100 resolved distributions, 220 metadata requests, 350 search states, 40 candidate versions per transitive distribution, 80 MB aggregate metadata response bytes, 35 MB per wheel, 110 MB total wheel bytes. Versions come from actual PyPI release metadata. Two fixed TLS registry hosts, verified public IPv4 destinations, no proxies, redirects, alternate indexes or arbitrary network destinations. JSON and archive bytes only on host; no wheel extraction/install on host. Registry metadata is advisory. A restricted VM verifies actual hash-bound wheel identities, dry-run resolution of original direct pins using constraints and wheelhouse, then a real hash-required offline install into a throwaway target (two audited pip handoffs). No package imports, application code or source builds. Exact target patch version is checked in the guest, not assumed. Default target 3.12.3 is the Ubuntu 24.04 pilot assumption; change only to an independently known actual guest version. Native wheel coverage is deliberately conservative. Registry metadata can differ from a wheel; mismatch fails rather than silently selecting a different graph. This is not a general pip resolver, and it cannot guarantee all compatible solutions within bounds.
* **8C.2C**: opt-in managed-run storage tripwire for npm and Python preparation, 14 GiB summed logical file lengths, 6 GiB free-space reserve, 250 ms polling, final sample and abort/no publication on measurement or termination uncertainty. Existing 1,536 MiB guest workspace is enforced. Windows volume GUID inspection can require a separate <=32 GiB volume with >=24 GiB free; capacity bounds files on that volume, not all process writes. **Polling is not a hard quota**. No changes to partitions, disks, ACLs, Windows firewall, or VM image. Legacy application VM execution is not covered by this new watchdog.
* **8C.2D/E**: reuse existing managed leased workspace, Windows Job Object, source-free guest probes, fixed worker path, independent host loopback positive control, app-UID connection denial, cgroup pre-exec observation, cleanup gates. No new independent dedicated worker identity or host-wide security attestation; a separate deployment is still needed.
* **8C.3**: one `dispatch` entry point; fresh pinned source, deterministic dependency-plan routing, optional inert package acquisition without per-repo VM approval, optional **reviewed-only** offline assembly and legacy reviewed readiness. Same-invocation successful prepared artifacts can be supplied via a temporary private config copy with unchanged exact-SHA approvals. No imported receipt can authorize execution. Static mode has max VM budget zero; reviewed readiness has max budget one. No automatic untrusted VM route exists. Multi-component resolvers and unsupported runtime adapters remain out of scope. No automatic test-oracle generation here.

## CLI

Run from ProjectIQ root with existing `.venv` (requires the already normally installed `packaging` library; check `python -c "import packaging"`). No new third-party library installation is performed by installer.

```
python -m projectiq_executioner.phase8c_final dispatch --repo URL --ref SHA --out FRESH_DIR --no-static
```

With no `--ref`, pin the resolved commit once and pass that exact SHA to subsequent stages. By default run existing STATIC orchestrator (unless `--no-static`). `--fetch` allows the fixed-purpose broker to make network requests for dependency data; no npm/pip is invoked on host. To test reviewed offline assembly, add `--assemble-reviewed --vm-config vm_config.json` plus the appropriate pinned assets. `--reuse-npm-bundle PATH` replaces `--fetch` for a previous 8C.2A bundle; the new path rechecks fresh reduced manifest and lock equality, exact outer ZIP member set, all tarball SHA-512 values and size limits, then copies the bundle. It never extracts tarballs on host. Reuse is single-component npm only. `--run-reviewed` explicitly requests one reviewed readiness attempt after successful assembly (or using existing operator profiles without assembly). The dispatcher does not create approval entries. If the worker fails, cleanup is uncertain, or the existing gate refuses, do not automatically retry. When readiness is requested, `reviewed_readiness_verified` requires the actual verified PASS suite, clean cleanup and exactly one scheduled VM attempt, not a general completion status. Reports mark automatic runtime permission false even when a separately authorized reviewed run takes place.

```
python -m projectiq_executioner.phase8c_final inspect-storage --vm-config vm_config.json --out FRESH_DIR
```

This uses actual Windows volume identity/capacity and is read-only. It returns 3, not a qualification PASS. Optional `--require-bounded-volume` on assembly refuses before launch if the observed volume does not meet the criteria. Do not attempt to force this on a personal system volume. The `run_8c_acceptance.ps1` kit script performs the coordinated tests. Default is read-only source/report checks and unit tests. `-Live` adds one Python reviewed preparation VM and one npm reviewed preparation VM using your previous bundle; `-Readiness` with `-Live` adds up to one reviewed application readiness VM for each. Stops on first unexpected failure. No unapproved repo launches. `--fetch` and `--reuse-npm-bundle` are mutually exclusive. No student code is executed by planning or broker; reviewed readiness runs only existing approved snapshots under legacy gate.

Exit 3 means completed with explicit limitations or inspection-only, 2 means blocked/failure. Read `dispatch_result.json` and nested receipts; do not use exit alone. Source and artifact hashes are consistency checks, not independent authenticity. `python-lock.json` is only a candidate until actual offline verification succeeds. If guest target mismatch occurs, obtain exact runtime version through an operator-owned clean diagnostic rather than guessing/retrying. If a PyPI wheel selection is unsupported, do not allow source builds as a workaround.

## Deployment prerequisites still outstanding (must be real, not fabricated config)

To qualify unknown student execution, provision a dedicated execution host (no personal files, credentials, connected accounts or private repository secrets), with a distinct restricted service identity and protected controller/guest image/worker binaries; isolation between controller and worker, and a mutually authenticated transport with non-replayable request/receipt identity. Put **all** worker write locations on a separately enforced fixed-capacity filesystem or quota, including logs, temporary files, image overlay and run artifacts; enforce process/memory/PID/time limits at the host boundary, not only within guest. Implement a network boundary independent of package parser/guest, deny access to host services, private networks and metadata endpoints, keep execution network-disabled and acquisition restricted to registry traffic. Independently verify QEMU/host patch and provenance, lifecycle termination and failure cleanup, unauthorized access denial and resource exhaustion controls on that deployed environment. Apply these controls to both preparation and application VMs. Do not equate current volume inspection, sampled watchdog, reviewed VM probes or a local signature with these prerequisites. Until that worker exists and is qualified, the automatic untrusted execution gate is deliberately closed. A genuine untrusted dispatch implementation and end-to-end acceptance against previously unseen *executed* repositories remain outstanding; the unseen-source acceptance in this kit is static/refusal only.

## Tests and evidence scope

The isolated regression combines previous phase payloads and representative integration fixtures with the new tests; simulated worker tests are not live QEMU acceptance. The actual local pip experiment uses a synthetic trusted wheel and no network; previous npm experiment likewise uses synthetic local archives. Live PyPI registry retrieval, Windows volume checks, actual guest pip/cgroup execution, guarded npm reassembly, ephemeral profile runtime integration and full-repo regression require the user's host. Never commit private config, wheelhouse/cache, downloaded packages, managed workspaces, or generated outputs. Existing 8C.2A live acceptance stays valid for the earlier unguarded worker path. This kit replaces only `phase8c2/worker.py` by a guarded opt-in change; all other files are additive.
